简介

档介绍了 Sahara 数据包结构、数据包流和预期用途。
Sahara 不提供使用本协议对发送的数据进行认证/验证的机制。这些机制超出本协议范围，可

在数据传输时与协议一起实施。

概述

Sahara 协议主要用于将软件映像从主机传输到目标。它提供了一种简单的机制，可通过任何

物理链路请求数据传输。
本协议支持两种基本数据包类型：命令包和数据包。命令包在主机和目标之间发送，以建立
数据包的传输。

2.1

目标驱动协议
本协议通过最小化主机和目标之间发送的命令包数量来最小化数据传输的开销。这是通过使
协议完全由目标驱动并通过让目标执行所有数据处理来完成的。主机只是等待数据传输请
求，其中包含以下信息：
■

要传输的数据映像

■

开始读取映像的偏移位置

■

数据传输长度

主机不需要处理或从实际映像数据提取任何信息 - 它只是将映像数据作为“原始”数据发送到
目标，而没有任何包头附加到数据包。由于目标发起了数据传输请求，因此它确切知道要接
收多少数据。这使得主机可在包头的情况下发送数据，并且目标可直接接收和存储数据。
目标根据需要从主机请求数据。它请求的第一个数据项是给定映像传输的映像头文件。一旦
目标处理了映像头文件，它就会知道映像中每个数据段的位置和大小。映像头文件还指定目
标内存中映像的目标地址。利用这些信息，目标可从主机为每个分段请求数据，并将数据直
接传输到目标内存中的适当位置。

2.2

数据包处理
本协议通过依靠物理传输层提供可靠的数据传输，从而最小化数据包处理。在协议层面，无
组帧、高级数据链路控制 (HDLC) 编码或循环冗余校验 (CRC) 应用到数据包。
每个命令包类型都有一个定义良好的结构，其中最少包含一个命令 ID 和数据包长度。利用这
些信息，可通过将接收到的命令包的长度与两个值之一进行比较来验证每个命令包的长度：
■

给定命令 ID 的预期数据包长度

■

数据包本身包含的长度字段

通过在每个数据包的末尾添加一个 CRC 字段，可轻松扩展 Sahara 以支持命令包验证。还可使
用各种鉴权方法验证数据包的数据完整性；不过，这超出了本协议的范围。

2.3

概述

同步通信
本协议假定主机和目标之间的所有通信都完全同步。从目标发送到主机的每个命令包都通过
从主机发送回目标的命令或数据包进行确认。同样，从主机发送到目标的每个命令包都使用
命令或数据包进行确认。
虽然主机和目标之间的链接预计是可靠的，但如果在从主机向目标发送命令包期间发生错
误，目标接收到错误的数据包，则目标会向主机发送错误响应并正常退出。
定时器机制可在主机和目标上实施，以支持在传输失败的情况下重新传输数据包。但是，这
种机制的实施超出了本协议范围 - 它仅指定在目标端收到意外或错误数据包时发生的情况。

2.4

可扩展性
本协议定义了一组固定的命令结构和数据包流。但是，它可轻松扩展以支持其他命令结构和
状态转换。

当任何映像数据从主机传输到目标时，此数据包用作通用数据传输包。它允许映像灵活地从
主机传输到目标。由于目标能够控制传输的数据，因此它能够决定传输映像中的哪一部分以
及以何种顺序进行传输。主机完全不需要了解映像结构；它只需要打开文件并基于数据包中
特定参数将数据传输到目标即可。这将给目标完整的控制权以对映像进行传输和处理。
主机在接收到该数据包后立刻就能用数据包响应。数据包必须只能包含映像数据且必须为读
取数据包所规定的长度。
当主机接收到读取数据包中如下的任何一个时，会出现错误：
■

无效或不支持的映像 ID

■

无效的数据偏移

■

无效的数据长度

如果上述任何字段无效，或主机上出现任何其他错误，主机会发送长度与目标所预期长度不
同的数据包。错误结果会迫使目标用 Status 字段中的错误码发送映像传输结束包（参见数据
包结构映像传输结束包）。该事务会使目标和主机进入错误处理状态。
当出现任何导致主机发送复位包的错误时，协议当前版本可以通过状态机实施（参见协议执
行）。

此数据包包含内存调试表的地址和长度。内存调试表是可以访问并转储到主机的内存位置列
表。表中的每一个条目都是具有如下类型的数据结构：
struct sahara_packet_memory_debug
{
uint32 command;
/* command ID */
uint32 length;
/* packet length incl command and length */
uint32 memory_table_addr;
/* location of memory region table */
uint32 memory_table_length;
/* length of memory table */
};

内存表的长度为结构的尺寸与表中条目的乘积。
在给定内存表地址和长度的情况下，主机可以发出内存读取来检索内存表。一旦主机接收到
内存表信息，就能够解码条目并发出内存读取请求来对每一个内存位置进行转储。

操作

数据包流程如下所述：
1. 目标将 Hello 包发送到主机以启动协议，将模式设置为映像传输待处理或映像传输完成

（取决于目标的启动序列）。
2. 在接收到 Hello 包并验证目标上运行的协议版本后，主机会发送带有“成功”状态的 Hello
响应包并将其模式设置为从 Hello 包接收的模式。
3. 一旦目标接收到 Hello 响应，目标将通过发送读取数据包启动映像传输请求。每个读取数

据包指定了目标期望接收的映像和传输哪一部分的映像。
4. 正常操作时，目标会先请求指定映像其他信息的映像头文件信息（即映像大小以及将在系

统内存的何处传输映像数据）。映像头文件（作为读取数据请求发送）的请求要求目标了
解将被传输的映像格式。本协议完全不需要主机了解映像格式，主机仅目标请求的映像中
读取并传输数据。
如果映像为独立的二进制映像且不含有任何数据分段，即数据在储存时和传输到目标系统
内存时是完全连续的，目标可以请求在一次传输中发送整个映像数据。如果映像数据是分
段的且要求将数据分段散射到非连续系统内存位置中，目标可以发出多个读取数据请求，
以使每个数据段都能直接传输到相应的目标地址。分散信息位于映像头文件中，由目标在
发出读取数据请求之前解析。
5. 主机在接收到读取数据请求后会解析映像 ID、数据偏移和数据长度以便从相应的映像文件

中传输数据。主机发送不带包头文件的请求数据。目标将数据直接传输到目标地址，不经
过任何系统内存中数据软件处理或临时缓冲。这将通过将映像头文件传输至目标并将用于
数据的接收缓冲器恰好设置为系统内存中的目标地址来实现。
6. 一旦目标成功接收映像的所有分段，目标便会发送带有与映像对应的映像 ID 和“成功”

状态的映像传输结束包。这能使主机停止读取并关闭映像文件。
7. 当接收到成功的映像传输结束后，主机发送完成包来允许目标退出协议。
8. 一旦目标接收到完成包，便会向主机发送完成响应包。在响应包中，目标表明其是否期望

传输另一个映像如果要向目标传输另一个映像，主机可以继续运行协议。

并行映像传输
本节介绍如何利用多线程环境并行传输多个映像。

单个主机、多个目标
如果主机可在硬件传输层上区分目标，且可将 Sahara 数据包路由到相应目标，则主机可在多
个线程上启动多个目标的状态机：
■

每个目标都会运行自身状态机来传输其希望传输的映像

■

主机需要运行线程管理器来发送/接收 Sahara 数据包并将其路由到相应的状态机

由于读取数据请求只需要指定映像 ID、数据偏移量和数据长度，主机只需要读取相应的映像
文件并将数据发送给请求目标。

多个主机、单个目标
如果目标需要传输多个主机的映像，则可将每个主机的连接封装到硬件传输层。在进入协议
时，目标可指定希望使用哪个硬件来传输给定的映像。目标可选择为每个映像进入和退出协
议，允许其选择每个映像使用的硬件传输层（通过使用调度表有效抽取相应软件驱动程序中
的主机连接）。每个主机都需要运行独立的状态机。

单个主机、单个目标、并行映像
如果目标想要从主机并行传输映像，则可在目标上使用线程环境（类似于单个主机、多目标
线程环境）。区别在于主机上不需要线程环境。目标需要对数据包到每个映像的状态机的路
由进行管理。
